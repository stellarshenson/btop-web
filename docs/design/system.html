Section 01

Foundation

The brand idea, the two-layer token model, and every semantic token measured against the pair it serves.

btop-web is btop's telemetry with the terminal removed. It keeps btop's panels, field names, units, precision and delta windows, and replaces braille glyphs, box-drawing borders and hotkey letters with a modern type and chart layer that reads on a desktop and a phone. Every visual decision answers one question: does this make the number more exact or more legible? A colour, a motion or a border that does neither is not in the system.

Two layers, one direction

The theme format carries 48 raw keys in btop's order (crates/btop-web/src/theme.rs:15-64; btop 1.3.0's built-in Default_theme carries 42 of them at src/btop_theme.cpp:49-91, and the Flexoki themes add the six banner and follow keys at crates/btop-web/themes/flexoki-dark.theme:108-115). Raw values stay verbatim. A missing key follows btop's own fallback rule, never a blanket fill from Default: meter_bg and graph_text from inactive_fg, and process_start/mid/end from cpu_start/mid/end (tmp/btop-src/src/btop_theme.cpp:272-287).

The semantic layer is the only layer a component reads. Each raw colour moves toward black or white only as far as its WCAG floor requires: 4.5:1 for text, 3:1 for focus, borders, status and charts (crates/btop-web/src/theme.rs:202-256,458-491). A raw value that cannot reach 3:1 is replaced by its clamped chart token rather than used directly. Raw values remain available for btop-faithful gradient fills.

Theme

Rows read --text, chart fills read --chart-cpu, control outlines read --border.

Five families, ten variants: Default, Gruvbox, Solarized, Everforest and Flexoki, each dark and light. The eight file-backed variants are the vendored crates/btop-web/themes/*.theme files; Default is generated from btop's Default_theme, with the light mode produced by an HSL lightness inversion (crates/btop-web/src/theme.rs:180-188,268-278). Every value below is parsed from the dashboard's own theme blocks, so this page cannot drift from docs/design/index.html.

Every semantic token per variant: value, the pair it is measured against, the measured ratio and the floor

PCHIP: Fritsch-Carlson monotone cubic interpolation

Every sparkline and every history chart is a PCHIP curve, never a polyline. Sample k lands on its timestamp, so the curve is exact at every knot; each interval stays inside the range of its two samples, so the curve cannot overshoot. The method is piecewise cubic Hermite interpolation with Fritsch-Carlson slopes (F. N. Fritsch and R. E. Carlson, "Monotone Piecewise Cubic Interpolation", SIAM Journal on Numerical Analysis 17(2):238-246, 1980, doi:10.1137/0717021).

dx   = 1 / (n - 1);   d_k = (y_(k+1) - y_k) / dx

interior slope, when d_(k-1) * d_k > 0:
  m_k = 2 d_(k-1) d_k / (d_(k-1) + d_k)
  m_k = 0 at a sign change
  |m_k| <= 3 * min(|d_(k-1)|, |d_k|)        the Fritsch-Carlson limit

endpoint slopes:
  m_0 = (3 d_0 - d_1) / 2
  m_(n-1) = (3 d_(n-2) - d_(n-3)) / 2
  the same zero rule and the same 3x clamp apply

Hermite form on each interval, sampled at 8 subdivisions:
  y(t) = h00 y_k + h10 dx m_k + h01 y_(k+1) + h11 dx m_(k+1)

PCHIP is O(n) time and O(n) memory: it solves no global system. A natural cubic spline solves a tridiagonal system; a bicubic scheme solves a 2D system. The implementation checks every evaluated point against the series minimum and maximum and would fall back to a straight polyline rather than draw an overshoot (docs/design/index.html:1933-2000).

The same twelve samples, two interpolation rules

Left: straight segments between knots. Right: PCHIP through the same knots. Both curves pass through every dot. The dots are the samples; PCHIP is exact there and stays between the adjacent sample values everywhere else. Stroke colours follow the active theme.

The replacement rule

A cubic or bicubic scheme may replace PCHIP only when its measured median rebuild at 120 knots is at least 20% faster on the target browser, and it passes the exact-knot and no-overshoot checks. When the times are similar (within 20%), PCHIP wins. Bicubic applies only to a 2D field; every series in this dashboard is one-dimensional, so the only candidate is a natural cubic.

Section 08

Performance budget

The dashboard reports the host's load; it must not become part of it. ACC-PERF-16-NO-OVERHEAD.

The server samples once per interval and fans the one snapshot out to every client. The browser applies a fragment when it arrives and does nothing in between. There is no timer, no requestAnimationFrame loop and no polling from the page.

Server rules

  • 1One interval, one watch channel, one snapshot per tick (crates/btop-web/src/collector/mod.rs:429-446).
  • 2Every SSE client reads the same snapshot; N clients cost no extra collection (crates/btop-web/src/routes/events.rs:64-117).
  • 3Static facts are cached: CPU model, core count, mount list, interface list and GPU inventory are read once and refreshed slowly, never per tick.
  • 4One tick, one fan-out: no per-client and no per-panel collection.

Status strip cost indicator

server tick 2.1 ms / 8 ms budget · within budget
server tick 11.4 ms / 8 ms budget · over budget
server tick 31.2 ms / 25 ms maximum · critical

The word carries the state. The thresholds are 8 ms (within budget), above 8 ms (over budget) and above 25 ms (critical). The readout is the last tick; the p95 is taken over five minutes.

Browser rules

  • 1Fragment-driven: apply a snapshot when a fragment arrives; no work between fragments.
  • 2No per-frame work: scrolling, hovering and resizing rebuild nothing.
  • 3Hidden tabs stop applying snapshots; the stream stays open and one resync runs on show.
  • 4A theme change restyles custom properties only; no chart is rebuilt.
  • 5One DOM write per region; the server may morph a fragment, the page does not replace the grid.

A 120-knot history is 952 path segments at 8 subdivisions per interval (119 intervals x 8). The measured PCHIP path build is 0.0995-0.1015 ms, so six history charts cost about 0.6 ms of script; the rest of the 4 ms per-chart budget is DOM assignment and paint. The 64-cell matrix and the process rows arrive in one fragment write.

What a component must never do

  • Start a timer, an interval or a requestAnimationFrame loop.
  • Poll while the SSE stream is open, or open a second stream for its own data.
  • Rebuild a chart on scroll, hover, resize or a theme change.
  • Animate a value, a chart or a fill width.
  • Collect, read /proc or call a device from the browser.
  • Replace the whole dashboard when one fragment arrives.
  • Keep applying snapshots while its tab is hidden.
  • Hide the tick cost, or report it without its threshold.

House alignment

From the house design system (the JupyterLab extension design language) this system takes four habits: the 4 px spacing rhythm with dense rows; state as separate attributes plus a word; honest focus rings on :focus-visible only, never removed; and restrained motion over colour and opacity. It takes no --jp-* token, no jp-* class name and no JupyterLab DOM.

One house habit is deliberately not followed: a control on a panel paints one 2% step toward the foreground rather than darker, because the btop palettes derive the step from the text direction and the same rule must hold in light and dark. The recessed reading is carried by --surface-sunken on the per-core cells, which no text token sits on except --text.

Where btop-web deliberately diverges from btop

  • Full values where btop truncates: load to two decimals, and 3.99 GHz where btop's short form is 4.0 GHz.
  • The 64-core matrix stays at every width; btop drops its list when the terminal column heuristic fails.
  • Unavailable is shown where btop hides a missing metric.
  • The disk list shows the statvfs mounts the collector reads, not the fstab entries; the use_fstab decision is open question Q4 in notes.md.

The panel names, field names, units, precision and delta windows stay btop's. A reviewer compares the page against btop running beside it; the numbers and the names must match, the pixels need not.
