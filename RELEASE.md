# Release

This file is the checklist a btop-web release must complete before it is called successful. Work through the boxes in order; each box names the command that proves it. `make version` prints the workspace version from `[workspace.package].version` in `Cargo.toml`, and this checklist expects `1.0.3`, up from `1.0.2`. A later release substitutes its own approved number for `1.0.3`.

## Checklist

- [ ] **1. Confirm the version** - the release number is `1.0.3`, up from `1.0.2`; it is written in `[workspace.package].version` in `Cargo.toml` and in the `btop-web` entry in `Cargo.lock`. A later patch release increments the number with `make increment_version_number`; any version change needs the owner's explicit approval at the time. Pass: `make version` prints `1.0.3` and `grep -A1 'name = "btop-web"' Cargo.lock` shows `version = "1.0.3"`
- [ ] **2. Update the libraries** - run `make upgrade`, then `make deny`, then `make sbom`. `make upgrade` runs `cargo update` and `cargo upgrade --incompatible`; `make deny` checks advisories, licences, bans and sources; `make sbom` regenerates `sbom.cdx.json` from `Cargo.lock`. Pass: `make upgrade` exits 0, `make deny` ends with `advisories ok, bans ok, licenses ok, sources ok`, and `make sbom` exits 0. The lines `cargo-deny not installed - skipping` and `cargo-upgrade not installed - install it with: cargo install --locked cargo-edit` are not passes; `make tools` installs the tools. `grep -A1 '"name": "btop-web"' sbom.cdx.json` shows `"version": "1.0.3"`
- [ ] **3. Build the release binary** - run `make doctor`, then `make build`; this build increments the patch to the released version `1.0.3`. Pass: `make doctor` reports the pinned toolchain `1.99.1`, an active toolchain that starts with `1.99.1`, and `present` for `cargo`, `rustup`, `cargo-deny`, `cargo-llvm-cov`, `cargo-release` and `cargo-edit`; the build exits 0; `target/release/btop-web --version` prints `btop-web 1.0.3`
- [ ] **4. Run the unit and functional tests** - run `make ci`. It runs `fmt-check`, `clippy` with `-D warnings` and `cargo test --locked --workspace --all-targets`. Pass: the command exits 0 and every `test result:` line reads `ok`. The unit tests are the `Running unittests src/lib.rs` and `Running unittests src/main.rs` sections; the functional tests are six sections: `Running tests/e2e.rs`, which boots the real binary against the recorded `/proc` and `/sys` trees; `Running tests/font.rs`, which checks the served font; `Running tests/http.rs`, which drives the HTTP routes; `Running tests/perf.rs`, which compares the process fragment with a recorded one and checks that the sampler parks and wakes; `Running tests/theme_contrast.rs`, which checks the contrast of every theme pair; and `Running tests/tls.rs`, which checks the agent's TLS listener and its certificate pinning. A `FAILED` line fails the release
- [ ] **5. Update the README** - README.md shows the release image at its top (currently `docs/design/owner-2026-10-30.png`). Replace it with a capture of the page served by the step 3 binary at 1440x900 in dark mode, with the top bar showing `1.0.3`; start `target/release/btop-web` on a free port, since the default `127.0.0.1:40290` may be in use. The Docker image tags in the same file name this release, so update them with it. Pass, after the capture is saved: `IMG=$(grep -o '(docs/design/[^)]*)' README.md | head -1 | tr -d '()') && find crates/btop-web/templates crates/btop-web/assets crates/btop-web/themes -type f -newer "$IMG"` prints nothing, `grep -n '1\.0\.3' README.md` names the Docker image line, and the image shows the shipped page. Before the capture, the same command lists every template and asset changed after the current image
- [ ] **6. Update the changelog** - add the release's changes under `## [1.0.3] - <release date>` in `CHANGELOG.md`, and leave an empty `## [Unreleased]` above it. Pass: `grep -n '^## ' CHANGELOG.md` prints `## [Unreleased]` first and `## [1.0.3] - <release date>` second, with the release's changes under the version heading
- [ ] **7. Update the journal** - append the release entry through the journal plugin with `/journal:update`; never edit `.claude/JOURNAL.md` directly. Pass: `journal-tools check .claude/JOURNAL.md` prints `OK: <n> entries, no violations.` and the last numbered entry is the release entry
- [ ] **8. Commit the preparation** - `make release` refuses a tree with uncommitted changes, so commit the files from steps 2 to 7 first. Run `git status --porcelain` to review, then `git add -A` and `git commit -m "chore: prepare release 1.0.3"`. The commit needs the owner's explicit approval at the time. Pass: `git status --porcelain` prints nothing and `git log -1 --oneline` shows the commit
- [ ] **9. Tag and push the release** - run `make release LEVEL=1.0.3` as a dry run, then, with the owner's explicit approval for the tag and the push, run `make release LEVEL='tag --no-confirm' EXECUTE=1`, then `make release LEVEL='push --no-confirm' EXECUTE=1`. Without `--no-confirm`, cargo-release asks `[y/N]` and, when it gets no `y`, exits 0 with no tag. `make release LEVEL=1.0.3 EXECUTE=1` is not used, because its plan starts with `git commit -am`, and that command exits 1 on the clean tree that step 8 leaves. Pass: the dry run prints `btop-web-v1.0.3` and the push of `main` to `origin` with no uncommitted-changes error; both executed runs exit 0; `git describe --tags --exact-match` prints `btop-web-v1.0.3`
- [ ] **10. Remove the temporary folders** - the live instance runs from `tmp/live`, so stop it first: `pgrep -x btop-web-owner` prints its pid, or nothing when it is not running, and `kill <pid>` stops that exact pid. Then run `for d in tmp target coverage graphify-out; do if [ -e "$d" ]; then trash-put "$d"; fi; done`. `trash-put` moves each folder to the trash, so it stays recoverable; never use `rm`, and do not use `make clean`, which deletes `target/` permanently. Pass: `ls -d tmp target coverage graphify-out 2>/dev/null` prints nothing
- [ ] **11. Check the cleanup** - pass: `git status --porcelain` prints nothing, so no release file is uncommitted, and `git status --ignored --porcelain | grep -E 'tmp/|target/|coverage/|graphify-out/'` prints nothing, so none of the four folders that step 10 removes remains
- [ ] **12. Wait for CI/CD to pass** - `git rev-parse --short HEAD` prints the release commit. Read the `CI` workflow at https://github.com/stellarshenson/btop-web/actions/workflows/ci.yml and the `Docker` workflow at https://github.com/stellarshenson/btop-web/actions/workflows/docker.yml. Pass: the newest `CI` run for `main` names the release commit and every job passes, and the `Docker` run for the release tag passes. The `Docker` workflow starts only for a tag that matches `btop-web-v*`, which `btop-web-v1.0.3` from `make release` matches; no run means the image was not published and the CI/CD check is not passed
- [ ] **13. Publish to crates.io** - with the owner's explicit approval at the time, run `make publish`. It refuses a dirty tree and a manifest still marked `publish = false`, then runs `cargo publish --locked -p btop-web` with the `cratesio/api` token from the vault through `jupyterlab-passkey vault exec`, so the token is never printed. `cargo publish --dry-run --locked -p btop-web` packages and verifies the crate without uploading. Pass: `make publish` exits 0, the crates.io page for `btop-web` shows the released version, and `cargo install btop-web` resolves it from the registry

## Stop rules

- A commit needs the owner's explicit approval at the time it is made
- A push needs the owner's explicit approval at the time it is made
- A tag needs the owner's explicit approval at the time it is made
- A version bump needs the owner's explicit approval at the time it is made
- A publish needs the owner's explicit approval at the time it is made; pushing the container image counts as a publish
- Approval for one step does not carry to the next step or to another release
- A failed `CI` or `Docker` run blocks the release; the release is not called successful while a run fails or is missing
